Sentinel chain of custody

Okta decides. Bifrost enforces. Every refusal below is Okta’s own wording; the gateway holds no policy of its own.

The four parties

WhoWhat it isWhat it is doing here
Okta Where identities live. Usually people. Here it also holds the agent’s identity and the rules about what it may do. Answering one question, over and over: would I give this agent a credential for this thing, right now? Yes, and it issues one that lasts minutes. No, and it says why.
Sentinel Watch Service Software that starts the work. Not a person, not an agent. A plain service account, like a scheduler. Asking for something to be done. It holds the only credential this web page ever sees, and it cannot do the work itself.
Bifrost The gateway every agent tool call passes through. The customer’s component, not Okta’s. Before each call, asking Okta if the agent is still allowed. Yes: attach a fresh short-lived credential and pass it on. No: stop the call. It holds no rules of its own.
Fleet Ops MCP server The system being protected. Cheap reads, plus one action that moves a physical asset. Checking the credential itself and reporting what it found. It does not take the gateway’s word for anything, so going around the gateway does not get you in.

Why chain of custody

Because “an agent did it” is not a useful answer.

With one shared accountWith chain of custody
You cannot tell which agent did what. The log shows the shared account. Every credential names who asked and which agent acted.
You cannot switch one agent off without switching off all of them. So nobody switches any off. Each agent has its own identity, so it can be stopped on its own.
Permissions grow to the widest thing anyone might need. Read-only agents end up with write access. Permissions are per agent, per resource, and checked on each call.

One honest limit. This says whether an agent may dispatch. It does not say whether it may dispatch that particular vehicle. Per-object rules are a separate layer on top.

Two questions people ask

Why can the agent still see a tool it may not use? Listing is not gated; running is. Hiding it adds no control, because a hidden tool still has to be refused when called directly.
Is Okta really asked on every call? The gateway evaluates every call and remembers Okta’s answer for a few seconds. That same window is how quickly switching an agent off takes effect, so it is a tradeoff, not a free dial.

What the plugin is

A small piece of code that loads inside Bifrost. Bifrost is not modified and not forked. The plugin is what makes the gateway ask Okta.

Open source, reusable by any Bifrost customer: oktaforai-okta/okta-bifrost-plugin

The demo you are looking at, including its Okta setup runbook: oktaforai-okta/fleetops-bifrost-demo

What it does, at two moments

WhenWhat it does
Connecting Gets a short-lived, agent-scoped token from Okta and attaches it to the upstream call. The token names both the calling service and the acting agent.
Every tool call Asks Okta again whether it would still issue that token. If not, the call is refused and never leaves the gateway.

Why ask twice

A credential that has been issued cannot be taken back. That is how access tokens work everywhere, not a flaw in Okta. So when you switch an agent off, two things are true at once: Okta will issue it nothing new, instantly, and the credential it already holds keeps working until it expires.

Closing that gap needs something that keeps asking. The only component that sees every call is the gateway. That is why this lives here and not somewhere more convenient.

Design choices worth knowing

Asking Okta to mint is the question Rather than reading an agent’s status from an admin API. The grant is the decision, it needs no second admin credential, and it exercises the same policy path the real call depends on.
A refusal is never returned as an error Bifrost treats a hook error as non-blocking, so refusing by error would let the call through. It short-circuits instead.
Answers are cached briefly Keyed on the exact question: authorization server, target, and the sorted scope set. The cache lifetime is also the revocation delay.
Known limit Catches an agent being switched off. Does not catch scopes being narrowed, because the token in flight keeps what it was granted at connect.

Proving this is real

In the Bifrost log

What to look for: one line per tool call, and the word that starts it.

tool handler success tool="fleetops_read-list_routes"

tool handler error   tool="fleetops_command-dispatch_vehicle"
  error=okta denied "fleetops_command-dispatch_vehicle" on "fleetops_command":
        id-jag exchange: invalid_scope: The following scopes are not allowed
        for this request: [task.dispatch]. (HTTP 400)
If you seeIt means
okta denied The per-call check fired. Okta was consulted on this call. This is the strong claim.
okta refused to issue a token for Refused at connect time. Also correct, but only proves the session could not start.
invalid_scope ... [task.dispatch] Okta’s own words, passed through. The gateway did not compose this.

Show it live with ./scripts/watch-gateway.sh, which filters Bifrost’s log to just these lines.

Reading the diagram: states, and what sub_profile means
  • idle, thin outline
  • in progress, dashed
  • issued, thick outline
  • refused, thick outline
  • no decision reached, dash-dot
  • not attempted, dotted

Refused and no decision are kept apart on purpose. Refused means Okta decided, and decided no. No decision means the call never got that far, so nothing about it can be attributed to Okta.

Every box and arrow also carries its state as text, so nothing depends on telling the colours apart.

sub_profile appears on a box only once a token has actually stated it. It is the token’s own answer to what KIND of principal each party is (service or ai_agent), rather than something inferred from a name. Before the first run the boxes carry no profile, because nothing has said one yet.
