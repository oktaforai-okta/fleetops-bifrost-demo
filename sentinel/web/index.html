Sentinel chain of custody

Okta decides. Bifrost enforces. Every refusal below is Okta’s own wording; the gateway holds no policy of its own.

The four parties

Okta

Okta is where identities live. Usually people; here it also holds the agent’s own identity and the rules about what that agent may do.

What it is doing here: answering one question, over and over. Would I give this agent a credential for this thing, right now? Yes, and it issues one that lasts minutes. No, and it says why.

Sentinel Watch Service

A piece of software that starts the work. Not a person and not an agent, just a plain service account, the sort of thing a scheduler or an alerting system would be.

What it is doing here: asking for something to be done, and holding the only credential this web page ever sees. It cannot do the work itself.

Bifrost

The gateway. Every tool call an agent makes passes through it. It is the customer’s existing component, not something Okta supplies.

What it is doing here: before each call it asks Okta whether the agent is still allowed. If yes, it attaches a fresh short-lived credential and passes the call on. If no, it stops the call. It holds no rules of its own, which is the point: swap the rules in Okta and the gateway’s behaviour changes with no redeploy.

Fleet Ops MCP server

The system being protected. A stand-in for a real operational one. It has cheap reads, telemetry and routes, and one action that moves a physical asset, dispatch. Those are not the same risk, so they do not carry the same permission.

What it is doing here: checking the credential itself, on its own, and reporting what it found. It does not take the gateway’s word for anything, so going around the gateway does not get you in.

Why chain of custody

Because “an agent did it” is not a useful answer.

Most agent deployments today share one account. Every call arrives looking identical, and three problems follow:

  • You cannot tell which agent did what. The log shows the shared account.
  • You cannot switch one agent off without switching all of them off, so in practice nobody switches any of them off.
  • Permissions grow to the widest thing anyone might need, so read-only agents end up holding write access.

Chain of custody means each credential carries two facts instead of one: who asked, and which agent acted. The receiving system is told both and can decide on both. That is what you are watching on the diagram.

One honest limit: this says whether an agent may dispatch. It does not say whether it may dispatch that particular vehicle. Per-object rules are a separate layer on top of this one.

Reading the diagram: states, and what sub_profile means
  • idle, thin outline
  • in progress, dashed
  • issued, thick outline
  • refused, thick outline
  • no decision reached, dash-dot
  • not attempted, dotted

Refused and no decision are kept apart on purpose. Refused means Okta decided, and decided no. No decision means the call never got that far, so nothing about it can be attributed to Okta.

Every box and arrow also carries its state as text, so nothing depends on telling the colours apart.

sub_profile appears on a box only once a token has actually stated it. It is the token’s own answer to what KIND of principal each party is (service or ai_agent), rather than something inferred from a name. Before the first run the boxes carry no profile, because nothing has said one yet.
