Sentinel chain of custody

Okta is the policy decision point. Bifrost is only the enforcement point. Every outcome below is Okta’s decision, and every refusal is Okta’s own wording. The gateway holds no policy: it asks, on every call, and obeys the answer.

Two demonstrations. Through the gateway makes a real MCP tool call, so you see the decision being enforced where it would be in production. Direct to Okta removes the gateway entirely, so you see the delegated token itself, decoded, with nothing in the middle.

Okta is drawn beside the flow rather than in it, because it is asked on every hop rather than being passed through. Select any box or arrow for the endpoint that was called and what came back.

The D3 library did not load from the CDN, so the diagram cannot be drawn. The step list below carries the same information as text.

  • idle, thin outline
  • in progress, dashed
  • issued, thick outline
  • refused, thick outline
  • no decision reached, dash-dot
  • not attempted, dotted

Refused and no decision are kept apart on purpose. Refused means Okta decided, and decided no. No decision means the call never got that far, so nothing about it can be attributed to Okta.

Every box and arrow also carries its state as text, so nothing here depends on being able to tell the colours apart.

sub_profile appears on a box only once a token has actually stated it. It is the token’s own answer to what KIND of principal each party is (service or ai_agent), rather than something inferred from a name. Before the first run the boxes carry no profile, because nothing has said one yet.
